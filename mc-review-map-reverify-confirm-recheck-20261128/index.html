🔍 方法论说明：为什么有的项网上核实不了
1. 线路↔列车映射本身，网上信息确实很多——维基百科各线路／车系条目、4gousya.net 编成表、运营商官方新闻稿与时刻表、ekitan／Navitime 时刻，三方交叉即可核实。本轮 A 类 16 项映射全部核实无误、D/E 类实车事实也全部网上核实。MC 的直觉是对的。
2. 纸模图纸是另一回事。图纸不在维基百科上，在 pepar.net、Canon／Brother 纸模站、爱好者站，以及项目自己的图纸库 rail-trainpdf。确认轮只查了公开网页，没查自家库——6 张图就躺在库里，其中 4 项的模型在重核期间已经建成。教训：以后凡称“图纸未确认”，须先查 rail-trainpdf 全树（8,197 文件），再查 pepar.net 站内检索（注意其 JS 检索文本爬取覆盖不到，须进站查），最后才是一般网页检索。
3. B 类数据字符串，网上真的核实不了。行程数据里用哪个字符串（「京阪宇治線」存不存在、「高尾登山ケーブル」还是「高尾登山電鉄」、ホームライナー key 覆盖哪几条线）是本站流水线内部的命名与归并选择，不是公开铁路事实。网上能查到“ホームライナー是什么车”，查不到“本站数据里这个 key 覆盖了哪几条线的班次”。这类项的正确核实方法是打开行程数据实测——本轮 4 项全部实测出唯一答案，无一悬置。
4. “未确认”不等于“无法核实”。本轮把确认轮的“未确认”逐项拆成四种：网上可核实（38 项有公开证据）、需内部数据（20 项须测数据）、图纸问题（24 项）、纯定夺（9 项）。只有第 4 种是“核实了也只能由 MC 定”，前三种都有确定答案。
5. 基线与数据集同一性必须先验明再实测。本轮两处重大发现都源于数据集不一致：确认轮 C-080 用的是过期 journey 数据集（2026-10-12，含「総武線」id 536），与测试站基线 live 数据（无「総武線」实体）不一致，按其修正案执行会造成 0 命中＋290 班误吞；确认轮 _meta.rules_engine 的 "names → lines → rules" 是过期标签，f786d0d 代码实为 names → rules → majority-line（2026-11-26 pathOf 修复一期）。以后凡涉及 rules 修法，须先对 data/tmaps.json blob SHA 与 app/app.js pathOf 原文验明，再谈修法。
